## 1. Что это за проект?

**Unicorn Messenger** (Мессенджер «Единорог») — это полноценный веб-мессенджер, созданный в рамках учебной практики в Омском государственном университете (ОмГУ, ФЦТМиК).

Это НЕ игрушечный проект, а рабочее приложение, в котором есть:

- **Регистрация и вход** по логину и паролю
- **Чаты** (групповые, личные, каналы)
- **Темы** внутри чатов (например, в чате «Работа» можно сделать тему «Фронтенд» и тему «Бэкенд»)
- **Отправка сообщений** в реальном времени (когда один пишет, другой видит сразу)
- **Пуш-уведомления** в браузере (если пользователь свернул вкладку, ему всё равно придёт уведомление)
- **Видеозвонки** прямо в браузере (WebRTC) — со своей технологией, которая работает даже через сложные сети (TURN сервер)

Простыми словами: это такой свой Telegram, только сделанный студентами.

## 3. Из чего состоит проект?

Проект разделён на **три большие части**:

```
┌─────────────────────────────────────────────────┐
│               Unicorn Messenger                  │
├───────────────────┬─────────────────────────────┤
│                   │                             │
│    Backend        │        Frontend             │
│  (серверная часть)│    (клиентская часть)       │
│                   │                             │
│  Язык: Go         │  Язык: TypeScript           │
│  Сайт: нет        │  Фреймворк: SvelteKit       │
│  Порты: 8080      │  Порты: 5173 (разработка)   │
│                   │        80 (готовый сайт)    │
├───────────────────┴─────────────────────────────┤
│                                                 │
│    WebRTC Service (сервер видеозвонков)         │
│                                                 │
│  Язык: Go                                       │
│  Порты: 8081 (HTTP), 3478 (UDP/TURN)            │
├─────────────────────────────────────────────────┤
│                                                 │
│    База данных: PostgreSQL                      │
│    Кеш/очереди: Redis (Valkey)                  │
│                                                 │
└─────────────────────────────────────────────────┘
```

**Если совсем просто:**
1. **Backend** — это «мозг» программы. Он хранит данные, проверяет пароли, отправляет сообщения.
2. **Frontend** — это «лицо» программы. То, что вы видите в браузере: кнопки, чаты, сообщения.
3. **WebRTC Service** — это «телефонная станция». Она помогает устанавливать видеозвонки.
4. **PostgreSQL** — это «шкаф с папками». Там хранятся все пользователи, сообщения, чаты.
5. **Redis** — это «курьер». Он быстро доставляет сообщения от одного пользователя к другому.

## 4. Как это работает? (общая схема)

Когда вы открываете мессенджер в браузере, происходит вот что:

```
Шаг 1: Вы вводите логин и пароль → Frontend отправляет запрос на Backend
Шаг 2: Backend проверяет пароль → выдаёт вам JWT-токен (это как пропуск)
Шаг 3: С этим пропуском вы заходите в приложение
Шаг 4: Frontend запрашивает список чатов → Backend отдаёт их из базы данных
Шаг 5: Вы нажимаете на чат → открываются сообщения
Шаг 6: Когда вы пишете сообщение:
        - Frontend отправляет его на Backend
        - Backend сохраняет в базу данных
        - Backend отправляет сообщение через Redis всем, кто в этом чате
        - Если человек не в браузере — ему приходит пуш-уведомление
Шаг 7: Всё это происходит за доли секунды
```

## 5. Технологии, которые тут используются

| Технология | Для чего используется | Уровень сложности |
|---|---|---|
| **Go** (язык программирования) | Написана серверная часть (backend) | Средний |
| **Svelte 5** (фреймворк) | Написана клиентская часть (то, что в браузере) | Средний |
| **SvelteKit 2** (мета-фреймворк) | Связывает Svelte с сервером, маршрутизация | Средний |
| **TypeScript** (язык) | Клиентская часть написана на TypeScript (JavaScript с типами) | Средний |
| **PostgreSQL** (база данных) | Хранит пользователей, чаты, сообщения | Начальный |
| **Redis / Valkey** (кеш) | Доставляет сообщения в реальном времени | Начальный |
| **WebRTC** (технология) | Видеозвонки прямо в браузере без плагинов | Сложный |
| **TailwindCSS 4** (стили) | Оформление страниц (CSS) | Начальный |
| **Docker** | Упаковка приложения в контейнеры для удобного запуска | Средний |
| **JWT** (токены) | Авторизация (кто вы и что вам можно) | Начальный |
| **Vite** (сборщик) | Собирает frontend в готовый сайт | Начальный |

## 7. Как всё установить и запустить?

### 7.1 Что нужно установить предварительно

1. **Git** — чтобы скачать проект (https://git-scm.com/)
2. **Go** — для серверной части (https://go.dev/dl/) версия 1.26+
3. **Node.js** — для клиентской части (https://nodejs.org/) версия 22+
4. **Bun** (или npm) — пакетный менеджер (https://bun.sh/)
5. **Docker Desktop** — для базы данных и Redis (https://www.docker.com/products/docker-desktop/)
6. **Терминал** — командная строка (в Windows: PowerShell, CMD, или лучше Git Bash)

**Как проверить, что всё установлено:**

Откройте терминал и введите команды:

```bash
go version        # Должно показать что-то вроде go version go1.26.1 windows/amd64
node --version    # Должно показать v22.x.x
npm --version     # Должно показать 10.x.x
bun --version     # Должно показать 1.x.x
docker --version  # Должно показать Docker version 27.x.x
```

Если какая-то команда не найдена — значит, соответствующую программу нужно установить.

### 7.2 Запуск базы данных

Сначала нужно запустить базу данных (PostgreSQL) и Redis (система доставки сообщений).

```bash
# Находясь в корневой папке проекта (C:\Users\user\messanger)
docker compose up postgres valkey
```

**Что произойдёт:**
- Запустится **PostgreSQL** на порту 5432 — база данных для хранения информации
- Запустится **Valkey** (копия Redis) на порту 6379 — для доставки сообщений в реальном времени

**Важно:** Не закрывайте это окно терминала! База данных должна работать всё время, пока вы пользуетесь мессенджером.

### 7.3 Запуск серверной части (backend)

Откройте **новое окно терминала** (первое окно занято базой данных).

Перейдите в папку backend и запустите сервер:

```bash
cd backend
go run cmd/main/main.go
```

**Что произойдёт:**
- Сервер прочитает настройки подключения к базе данных
- Создаст все необходимые таблицы (если их ещё нет) — это называется «миграции»
- Запустит веб-сервер на порту 8080

Когда появится надпись `Starting server on :8080` — всё работает!

### 7.4 Запуск клиентской части (frontend)

Откройте **третье окно терминала**.

```bash
cd frontend
bun install      # Установить зависимости (делается один раз)
bun run dev      # Запустить сервер разработки
```

Когда появится надпись `http://localhost:5173` — откройте этот адрес в браузере.

### 7.5 Запуск WebRTC сервера (видеозвонки)

Если вам нужны видеозвонки, откройте **четвёртое окно терминала**:

```bash
cd webrtc_service
go run .
```

### 7.6 Запуск всего одной командой

Можно запустить всё сразу одной командой:

```bash
docker compose up
```

Но это будет работать только если вы не меняли код (Docker использует готовые образы).

## 8. Как пользоваться мессенджером?

### Шаг 1: Откройте сайт

Перейдите по адресу: `http://localhost:5173`

### Шаг 2: Зарегистрируйтесь

### 9.2 Серверная логика (backend на Go)

Сервер работает по принципу: **запрос → обработка → ответ**.

**Как устроен сервер (слои):**

```
Запрос от браузера (HTTP)
       │
       ▼
┌─────────────────────┐
│    Middleware        │ ← Проверка: разрешён ли запрос?
│  (промежуточные     │    - CORS: пускать ли запросы с других сайтов?
│   обработчики)      │    - Логирование: записать, кто и что запросил
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│   Controller        │ ← Приём запроса, разбор параметров
│  (контроллер)       │    - Извлечь ID пользователя из URL
│                     │    - Прочитать JSON из тела запроса
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│    Service          │ ← Бизнес-логика (самое главное)
│   (сервис)          │    - Проверить, имеет ли пользователь доступ
│                     │    - Сохранить сообщение в БД
│                     │    - Отправить уведомление
└─────────┬───────────┘
          ▼
┌─────────────────────┐
│   Repository        │ ← Работа с базой данных
│  (репозиторий)      │    - SQL запросы к PostgreSQL
│                     │    - Сохранить / прочитать / удалить данные
└─────────┬───────────┘
          ▼
    База данных
   (PostgreSQL)
```

## 10. Как работает авторизация?

Авторизация — это способ убедиться, что вы — это вы.

**Как это происходит:**

```
Шаг 1: Вы вводите логин и пароль
Шаг 2: Сервер проверяет:
        - Есть ли такой пользователь в базе?
        - Совпадает ли пароль? (пароль хранится в зашифрованном виде — bcrypt)
Шаг 3: Если всё верно — сервер создаёт JWT-токен
        JWT — это строка вида: "eyJhbGciOiJIUzI1NiIs..."
        В этой строке зашифрованы: ваш ID, имя, срок действия
Шаг 4: Браузер сохраняет этот токен
Шаг 5: При каждом следующем запросе браузер отправляет токен в заголовке:
        Authorization: Bearer eyJhbGciOiJIUzI1NiIs...
Шаг 6: Сервер проверяет токен и понимает, кто вы
```

**Что такое JWT-токен?**
Это как электронный пропуск. Вы получаете его при входе и показываете при каждом действии. В нём нельзя подделать данные, потому что он подписан секретным ключом сервера.

## 11. Как работает отправка сообщений в реальном времени?

Обычно, чтобы получить новое сообщение, нужно обновить страницу. Но в мессенджере сообщения приходят мгновенно. Как это сделано?

**Технология: SSE (Server-Sent Events) + Redis Pub/Sub**

```
                     ┌──────────┐
   ┌────────────────→│  Redis   │←────────────────┐
   │                 │ (очередь)│                  │
   │                 └──────────┘                  │
   │                                               │
   ▼                                               ▼
┌────────┐                                  ┌──────────┐
│Пользователь│  ───→  ┌──────┐  ───→   │Пользователь │
│  А        │        │Backend│         │  Б          │
└────────┘         └──────┘         └──────────┘
```

**Пошагово:**

1. Пользователь А открывает страницу и подписывается на события через SSE
   (SSE — это специальная технология, когда сервер может сам отправлять данные браузеру)

2. Пользователь А пишет сообщение → браузер отправляет его на backend

3. Backend сохраняет сообщение в базу данных

4. Backend публикует сообщение в Redis (в канал этого чата/темы)

5. Backend проверяет: кто ещё подписан на этот чат через SSE?
   - Если пользователь Б подписан → отправляем ему сообщение через SSE
   - Если пользователь Б не подписан → отправляем через Web Push (см. раздел про уведомления)

## 12. Как работают уведомления?

Если пользователь свернул вкладку или открыл другой сайт, он всё равно получит уведомление о новом сообщении.

**Технология: Web Push (VAPID)**

```
            Сервер
              │
              │ (HTTP POST)
              ▼
   ┌──────────────────┐
   │ Push Service      │ (браузерный сервер уведомлений)
   │ (Google/Apple/Mozilla) │
   └──────────────────┘
              │
              ▼
     ┌──────────────┐
     │  Браузер      │
     │  пользователя │
     └──────────────┘
              │
              ▼
        Уведомление на экране:
        "Иван: Привет!"
```

**Как это работает:**

1. При входе в мессенджер браузер спрашивает: «Разрешить уведомления?»
2. Если пользователь разрешил, браузер создаёт специальную подписку (push subscription)
3. Эта подписка отправляется на сервер и сохраняется в базе данных
4. Когда приходит новое сообщение, а пользователь не в чате:
   - Сервер берёт его подписку из базы данных
   - Отправляет запрос в Push Service (Google/Apple/Mozilla)
   - Push Service доставляет уведомление в браузер пользователя
   - Даже если сайт закрыт — уведомление всё равно придёт!

## 13. Как работают видеозвонки?

Видеозвонки — самая сложная часть. Они используют технологию WebRTC.

**Простое объяснение:**

WebRTC позволяет двум браузерам общаться напрямую, без посредников. Но есть проблема: компьютеры часто находятся за маршрутизаторами (NAT), и напрямую соединиться не могут.

**Как это решается:**

```
┌──────────┐          ┌──────────┐
│ Браузер  │          │ Браузер  │
│    А     │          │    Б     │
└────┬─────┘          └────┬─────┘
     │                     │
     │   ┌─────────────┐   │
     └──→│ WebRTC Server│←──┘
         │ (сигналинг)   │
         └──────┬───────┘
                │
         ┌──────┴───────┐
         │  TURN Server │ ← Если напрямую не получается,
         │  (релей)      │    видео идёт через этот сервер
         └──────────────┘
```

**Пошагово:**

1. Пользователь А заходит на страницу видеоконференции
2. Браузер А подключается по WebSocket к WebRTC серверу
3. Браузер А создаёт «предложение» (offer) и отправляет его на сервер
4. Сервер передаёт это предложение браузеру Б
5. Браузер Б отвечает «согласием» (answer)
6. Браузеры пытаются соединиться напрямую (через STUN)
7. Если не получается — используют TURN сервер (видео идёт через сервер)
8. Соединение установлено! Можно общаться

**Термины:**
- **WebSocket** — постоянное соединение между браузером и сервером
- **STUN** — сервер, который помогает узнать свой внешний IP-адрес
- **TURN** — сервер, который ретранслирует видео, если напрямую не соединиться
- **SDP** — формат описания, какое видео/аудио будет передаваться
- **ICE** — протокол, который ищет лучший путь для соединения

## 14. Swagger — что это и зачем?

Swagger — это автоматическая документация API. Представьте, что backend — это ресторан, а API — это меню. Swagger — это красивое меню с картинками, где написано, какие блюда (запросы) можно заказать и что для этого нужно.

**Где найти Swagger?**

После запуска backend откройте в браузере: `http://localhost:8080/docs/`

Там вы увидите все доступные запросы:
- `POST /register` — зарегистрироваться
- `POST /login` — войти
- `GET /me` — получить информацию о себе
- `GET /chats` — список чатов
- `POST /chats` — создать чат
- И так далее...

Для каждого запроса указано:
- Какой метод (GET, POST, PUT, DELETE)
- Какие параметры нужно передать
- Какой ответ ожидать

## 15. Советы для разработки

### Горячая перезагрузка (live reload)

Чтобы не перезапускать backend вручную после каждого изменения, используйте `air`:

```bash
# Установите air
go install github.com/air-verse/air@latest

# Запустите с конфигом из backend
cd backend
air
```

Теперь при изменении любого .go файла сервер перезапустится автоматически.

### Генерация кода для базы данных

Если вы изменили SQL-запросы в `internal/queries/`, нужно перегенерировать код:

```bash
cd backend
sqlc generate
```

### Обновление Swagger документации

Если вы изменили API, обновите документацию:

```bash
cd backend
swag init
```

### Полезные команды frontend

```bash
bun run dev          # Запустить в режиме разработки
bun run build        # Собрать готовый сайт
bun run check        # Проверить типы (TypeScript)
bun run lint         # Проверить код (ESLint)
```

### Ошибки и их решение

| Ошибка | Что делать |
|---|---|
| `port 8080 already in use` | Занят порт. Закройте другие программы или измените порт. |
| `connection refused` | База данных не запущена. Запустите `docker compose up postgres`. |
| `cannot find package` | Не установлены зависимости. Запустите `go mod download` или `bun install`. |
| `not found` (404) | Проверьте адрес в браузере. Может, забыли запустить frontend? |
